# 2026.06.12 작업 보고서

## 특허 분석 즐겨찾기 기본 폴더 중복 생성 방지

- 문제: 특허 분석 리스트에서 여러 즐겨찾기 추가 요청이 거의 동시에 들어오면, 각 요청이 동일한 폴더 트리 상태를 조회한 뒤 `myworkspace` 기본 폴더 생성을 중복 호출할 수 있었다.
- 원인: 기존 로직은 `GET-PATENT-LIST`로 폴더 트리를 조회하고 `myworkspace`/`ownerId` 폴더가 없으면 생성하는 체크는 있었지만, owner별 resolve/create 과정이 직렬화되어 있지 않았다.
- 수정: `backend/src/patent-analysis/patent-analysis.service.ts`에 owner별 `favoriteFolderResolveLocks`를 추가해 동일 owner의 기본 즐겨찾기 폴더 resolve/create 요청을 하나의 Promise로 공유하도록 했다.
- 추가 수정: helper/UI에서 폴더명이 `myworkspace/`처럼 trailing slash를 포함해 내려오는 경우도 기존 `myworkspace`로 인식하도록 폴더명 비교를 정규화했다.
- 추가 수정: 이미 중복 root가 있는 경우 `{ownerId}` 하위 폴더가 존재하는 `myworkspace` root를 우선 재사용하도록 했다.
- 추가 수정: resolve된 기본 즐겨찾기 folder id를 owner별 메모리 캐시에 저장해 같은 서버 인스턴스에서 반복 즐겨찾기 추가 시 폴더 트리 재조회/생성 경로를 다시 타지 않도록 했다.
- 추가 수정: 폴더 트리 확인 API를 원본 `patent_files` 화면과 동일하게 `GET-TARGET-LIST`로 변경했다. 기존 `GET-PATENT-LIST`는 특허 목록 조회 목적의 endpoint라 폴더 중복 체크 기준으로 쓰기 부적절할 수 있다.
- 추가 수정: `GET /api/patents/favorites` 조회 endpoint를 추가했다. 이 endpoint는 `GET-TARGET-LIST`의 기본 폴더 `patents[].publication_number`를 반환하며, 조회 중에는 폴더를 새로 생성하지 않는다.
- 추가 수정: 특허 분석 리스트 페이지 로드 시 즐겨찾기 publication number 목록을 Set으로 보관하고, 리스트 row 및 구조검색 하위 특허 row의 `isFavorite` 표시를 해당 Set 기준으로 보정한다.
- 영향 범위: `POST /api/patents/favorites`, `POST /api/patents/favorites/remove`, `POST /api/patents/favorites/share`, `GET /api/patents/my?favoriteOnly=true`에서 기본 폴더 resolve 시 동일 로직이 적용된다.

## Patent Insight heatmap에서 특허 리스트 검색 연동

- `Target x Applicant heatmap` cell 클릭 시 특허 분석 리스트로 이동하도록 했다.
- Insight heatmap 데이터에 `applicant`가 있으면 x축을 Applicant로 사용하고, 클릭 시 `target + applicant + 현재 Insight 기간` 조건을 전달한다.
- `applicant`가 없는 구버전/mock 응답은 기존처럼 연도 x축을 사용하고, 클릭 시 `target + 해당 연도` 조건을 전달한다. Insight 화면의 Applicant 검색어가 있으면 함께 전달한다.
- 이동 URL은 `/patents/analysis?source=insight&target={target}&applicant={applicant}&dateFrom={YYYY-MM-DD}&dateTo={YYYY-MM-DD}` 형식을 사용한다.
- 특허 분석 리스트는 최초 진입 시 URL query를 읽어 검색조건을 자동 바인딩한다.
  - `target` → Target 필터
  - `applicant` → 출원인 검색어
  - `dateFrom/dateTo` → 직접설정 기간
- Query 기반 초기 상태는 리스트 조회 API 호출 전에 적용되므로, 이동 직후 해당 조건으로 목록이 조회된다.
- Heatmap cell click용 부가 데이터를 추가하면서 색상 기준 dimension이 흔들릴 수 있어 `visualMap.dimension=2`, `series.encode.value=2`를 명시했다.

## MyBoard 그룹 상세 목록 구조 SVG 표시 UX

- 그룹 상세 목록의 `화합물 구조` 컬럼에서 RDKit SVG 생성 시 `min_size`를 강제하지 않도록 했다.
- RDKit이 반환한 SVG의 intrinsic width/height를 compound별로 캐시하고, 현재 상세 목록에 표시되는 SVG 중 가장 큰 width/height를 구조 프레임 크기로 사용한다.
- 행 높이는 최대 구조 프레임 기준으로 동일하게 맞추되, 각 SVG 자체는 `contain` 모드로 렌더링해 RDKit이 반환한 원래 크기와 비율을 유지한다.
- 구조 컬럼 width도 최대 SVG width 기준으로 동적으로 늘려 큰 구조가 잘리지 않도록 했다.
- 최대 구조 높이는 250px로 제한했다. 가장 큰 SVG가 250px을 넘으면 `250 / 최대 SVG 높이`를 공통 배율로 계산하고, 각 구조 이미지는 자기 원본 width/height에 해당 공통 배율을 곱한 크기로 표시한다. 예를 들어 높이 360px, 270px 구조가 있으면 360px을 250px로 줄이는 같은 배율을 270px 구조에도 적용한다.
- 단일 그룹만 선택된 경우에는 기존 UX처럼 그룹별 Scale 설정(`myBoardImageScalePercent`)을 적용한 고정 프레임과 RDKit `min_size` 기준으로 표시한다. 여러 그룹 선택 시에만 250px 기준 공통 배율 UX를 적용한다.
- MyBoard 구조 Scale 조절 상한을 120%에서 160%로 올렸다.

## SAR 페이지 화합물 카드 영역 구조 표시 UX

- SAR 페이지에서 여러 그룹이 선택된 경우, 화합물 카드 영역에 표시된 화합물들의 SVG 원본 높이 중 최대값을 기준으로 공통 배율을 계산한다.
- 최대 높이가 380px을 넘으면 `380 / 최대 SVG 높이` 배율을 화합물 카드 영역의 구조 이미지에 동일하게 적용한다.
- 단일 그룹 선택 모드에서는 카드가 여러 장 표시되더라도 기존 SAR Scale 설정과 정사각 RDKit `min_size` 표시 방식을 유지해 구조가 카드 영역을 꽉 채우도록 한다.
- 여러 그룹이 선택된 상태에서는 일반 구조 SVG와 cluster highlight SVG 모두 `min_size` 강제를 제거해 원본 SVG 크기 기준으로 공통 배율이 적용되도록 했다.
- 여러 그룹이 선택된 상태에서도 카드의 구조 부모 영역은 기존 정사각 크기로 유지하고, 축소된 SVG만 부모 중앙에 배치해 구조 위치와 하단 텍스트 위치가 카드별로 흔들리지 않도록 했다.
- 여러 그룹이 선택된 다중 모드에서는 draw API에 `min_size`를 보내지 않고, SAR Scale 설정은 `scalePercent`로만 전달한다.
- 기존 `min_size`로 생성되어 `rdkitSvg`에 남아 있던 캐시가 다중 카드 크기 계산에 섞이지 않도록, 다중 카드 모드에서는 현재 no-`min_size` render cacheKey의 SVG 크기를 우선 사용하고 없을 때만 raw SVG를 fallback으로 사용한다.
