# 2026-06-11 작업 보고서

## 1. PDF Highlight Box Click

### 배경
- `sample/patent_analysis_helper_html/portal.html`의 PDF highlight click 동작을 React 구현과 비교했다.
- 샘플은 PDF bbox를 `.highlight-box` overlay로 렌더링하고, 해당 box에 직접 click handler를 연결한다.
- 우리 구현은 `react-pdf-highlighter-plus`의 `AreaHighlight`를 감싼 wrapper와 Ant Design table 이동 로직을 사용한다.

### 샘플 동작 요약
- `highlight_bboxes`는 table/compound의 bbox 및 page 데이터로 구성된다.
- `renderPage`는 현재 page의 `.highlight-box`를 생성하고 `data-bbox-index`, `pageNum`, compound/table 식별자를 부여한다.
- `goToPdfBBoxByIndex`는 page 전환 후 실제 highlight box를 중앙으로 이동시키고 flash 상태를 준다.
- `.highlight-box` 클릭 시 `patent_compound_id`를 읽어 embodiment tab으로 전환하고, matching row page로 paginate한 뒤 관련 compound를 강조한다.

### 1차 시도 (동작 실패)
- `frontend/src/components/patent-analysis/pdf/PatentPdfHighlightContainer.tsx`
  - 절대 배치 `inset: 0` clickable wrapper를 제거하고, `display: contents` wrapper + `AreaHighlight`에 pointer event를 적용하는 방식으로 변경했다.
- `frontend/src/pages/PatentAnalysisDetail.tsx`
  - PDF bbox click 시 source metadata 기반으로 Raw/Clean table row로 이동하도록 routing을 보강했다.
- 결과: **블루 bbox를 클릭해도 `handlePdfHighlightClick`이 전혀 호출되지 않았다** (hover 시 pointer cursor도 표시되지 않음).

### 근본 원인 (디버깅으로 확인)
- `react-pdf-highlighter-plus`의 라이브러리 CSS:
  - `.PdfHighlighter__highlight-layer { pointer-events: none }` 이고, 직계 `> div` 자식 및 특정 클래스에만 `pointer-events: auto`가 적용된다.
- `AreaHighlight`는 내부적으로 `react-rnd`(드래그/리사이즈) 컴포넌트라 click 이벤트가 wrapper로 버블링되지 않는다.
- `display: contents` wrapper는 자체 box가 없어 자식 버블링에만 의존 → Rnd가 click을 소비하면 handler가 영영 호출되지 않는다.
- 디버그 로그로 확인한 결정적 사실: HighlightContainer 컨텍스트의 `highlight.position.boundingRect`는 라이브러리가 **이미 렌더 뷰포트 픽셀(`left`/`top`/`width`/`height`)로 변환**해 넘겨준다. (`x1`/`y1`/`x2`/`y2`가 아님)

### 최종 해결
- `frontend/src/components/patent-analysis/pdf/PatentPdfHighlightContainer.tsx`
  - `AreaHighlight`(Rnd)에 click을 의존하지 않고, **bbox 위에 투명 오버레이 `div`(`position: absolute`, 인라인 `pointer-events: auto`)** 를 얹어 click을 직접 받는다.
  - 오버레이 좌표는 `boundingRect`의 `left/top/width/height`를 **스케일 환산 없이 그대로** 사용 → 블루 박스와 정확히 겹친다.
  - 클릭 가능한 data bbox의 `AreaHighlight`는 `pointerEvents: 'none'`으로 두어 Rnd가 click을 가로채지 않게 했다.
  - `boundingRect` 환산이 불가능한 경우에만 기존 버블링 방식으로 fallback 한다.
- `frontend/src/pages/PatentAnalysisDetail.tsx`
  - `handlePdfHighlightClick`에서 source의 `scope`(raw/clean)와 `rowIndex`로 Raw/Clean table tab 전환·pagination·`activeCompId` 설정·row scroll을 수행한다.
  - Ant Design Table `scrollTo({ key })` + table pagination render 이후 delayed retry로 row를 포커싱한다.

### 블루 bbox 클릭 시 레드(선택) 표시
- `frontend/src/hooks/usePatentPdfViewer.ts`
  - `selectedDataHighlightId` 상태를 추가하고, `dataHighlights`의 각 항목 `source.selected = (id === selectedDataHighlightId)`로 토글한다.
  - `selectedDataHighlightId` / `setSelectedDataHighlightId`를 hook 반환에 노출한다.
- `frontend/src/pages/PatentAnalysisDetail.tsx`
  - `handlePdfHighlightClick`에서 클릭한 `highlight.id`로 `setSelectedDataHighlightId`를 호출 (단일 선택 → 다른 박스 클릭 시 레드가 이동).
- 레드 스타일(`isDataBboxSelected` → `3px solid rgba(255,0,0,0.92)` 테두리 + 연한 빨강 배경)은 `PatentPdfHighlightContainer`에 이미 정의되어 있어 `source.selected`만 켜지면 블루 → 레드로 전환된다.

#### 다중 red 버그 수정 (단일 선택 강제)
- 증상: bbox를 여러 번 클릭해 선택을 옮기면 이전에 선택된 box가 red로 남아 red가 여러 개가 됐다.
- 원인: 하이라이트 `id`가 선택 여부와 무관하게 고정(`raw_data_bbox_${id}`)이라, `source.selected`만 바뀌면 `react-pdf-highlighter-plus`가 리렌더(테두리 갱신)를 건너뛰어 이전 red DOM이 그대로 남았다.
- 해결: `usePatentPdfViewer`에서 선택된 항목만 `id`에 `__selected` 접미사를 붙여 **강제 remount**시키고, 선택 매칭은 `source.baseId`(접미사 없는 base id) 기준으로 유지했다. `handlePdfHighlightClick`은 `source.baseId`로 `setSelectedDataHighlightId`를 호출(이미 선택된 box 재클릭 시에도 deselect되지 않음).
- 결과: 현재 활성 box만 red, 나머지는 blue로 정상 표시된다.

#### 두 red 메커니즘 상호 배타 처리
- 증상: 우측 탭/카드 클릭으로 생기는 red(`active_compound_highlight`)와 좌측 blue box 클릭으로 생기는 red(`selectedDataHighlightId`)가 서로 독립적이라, 둘 다 켜지면 red가 2개가 됐다.
- 해결:
  - `usePatentPdfViewer.handleGoToPdf`(우측 활성화)에서 `setSelectedDataHighlightId(null)`로 좌측 blue 선택을 해제한다.
  - `usePatentPdfViewer`에 `clearActiveCompoundHighlight`(systemHighlights/activeBBox/pendingHighlight 초기화, rebump 키 리셋)를 추가하고, `handlePdfHighlightClick`(좌측 blue 클릭)에서 호출해 우측 active red를 제거한다.
  - `activeBBox`가 null이 되면 rebump effect의 cleanup이 예약된 600ms 타이머를 취소해 red가 되살아나지 않는다.
- 결과: 우측/좌측 어느 쪽으로 활성화해도 red는 항상 하나만 유지된다.

#### 블루 bbox 위치 어긋남(렌더 타이밍 레이스) 수정
- 증상: ① 가끔 진입 직후 블루 bbox가 어긋난 위치에 그려지고 리로드하면 정상, ② 스크롤로 아래 페이지를 볼 때도 어긋남.
- 원인: 블루 bbox의 화면 위치는 라이브러리가 렌더된 페이지(textLayer)의 실제 크기를 읽어 계산한다.
  - ① `pdfScaleValue="page-width"`라 PDF 패널 폭(`calc(${splitRatio}% …)`)이 정착되기 전 transient 크기로 위치 계산되면 어긋난 채 남았다.
  - ② 페이지 가상화(lazy render)로 스크롤 중 새 페이지가 렌더될 때, 그 페이지 textLayer가 최종 크기에 도달하기 전 위치 계산되면 어긋난다. 스크롤은 컨테이너 크기·스케일을 바꾸지 않아 ResizeObserver/scalechanging로는 잡히지 않는다.
- 해결: `usePatentPdfViewer`에 `highlightLayoutRevision` + trailing 디바운스(150ms) `bumpHighlightLayout` 추가, 아래 신호에서 bump.
  - PDF 뷰어 컨테이너 `ResizeObserver`(초기 정착·split 드래그·썸네일 토글·창 리사이즈).
  - pdf.js eventBus `scalechanging`/`rotationchanging`(스케일 확정/변경).
  - pdf.js eventBus `textlayerrendered`/`pagerendered`(스크롤 중 새 페이지 렌더 완료 시점).
  - `dataHighlights` 의존성에 `highlightLayoutRevision`를 포함해 새 객체 참조로 재생성 → 라이브러리가 최종 페이지 크기로 위치를 다시 계산.
- 성능: 처음엔 rAF 즉시 bump였으나, bbox가 많은 특허에서 스크롤 중 페이지 렌더 이벤트마다 전체 하이라이트가 재렌더되어 버벅였다. → **trailing 디바운스(150ms)** 로 변경해 스크롤 중에는 재계산을 미루고 멈춘 뒤 1회만 재정렬하도록 했다.
- 결과: 진입 직후·폭 변경·스크롤로 새 페이지 렌더 시 모두 블루 bbox가 올바른 위치로 (재)배치되며, 스크롤이 매끄럽다.

### 동작 확인 (완료)
- 블루 bbox 클릭 시 `handlePdfHighlightClick` 호출 및 우측 Raw/Clean table tab 전환·row 포커싱 동작 확인.
- 클릭한 블루 bbox가 레드로 전환되고, 다른 bbox 클릭 시 레드가 이동하는 것 확인.

### 남은 보강 포인트
- `scrollFocusedTableRow`는 `rAF` + 120ms 재시도 1회뿐이라 pagination 직후 가상 행 렌더 전이면 scroll이 빗나갈 수 있다 → 재시도 횟수/간격 보강 검토.
- clean row를 `buildCleanRowsFromPatentResult`(`:164`)와 `buildCleanRows`(`:975`) 두 곳에서 별도 생성 → `__rowKey` 정합성 위해 한 곳으로 통일 검토.

## 3. Transparent Structure Image Copy

### 배경
- 구조 이미지 복사는 SVG를 PNG로 변환한 뒤 clipboard에 기록한다.
- canvas 자체는 투명하지만, 일부 SVG는 전체 canvas를 덮는 흰색 background rect를 포함해 복사 결과에 흰 배경이 생겼다.

### 변경 내용
- `frontend/src/components/common/CompoundStructureView.tsx`
  - PNG 변환 전 SVG background stripping을 추가했다.
  - root SVG의 `background`/`background-color` style attribute를 제거한다.
  - stroke가 없고 전체 canvas를 덮는 흰색 `rect`만 제거한다.
  - molecule drawing element는 유지한다.

### 기대 결과
- 카드 및 enlarged preview modal의 이미지 복사가 배경 없는 투명 PNG로 동작한다.
- 분자 자체에 포함된 흰색 도형은 제거하지 않고, 전체 배경용 흰 박스만 제거한다.

- 한 번 열린 탭의 heavy DOM을 유지해 반복 탭 이동 시 remount 비용이 줄어든다.
- 탭 전환 시 forced reflow 및 click handler 지연 빈도가 줄어든다.
- 데이터 로드 중에는 "데이터가 없습니다"보다 로딩 상태가 먼저 보여 혼동이 줄어든다.

## 20. PDF 텍스트 검색 한글(IME) 지원

### 배경
- PDF 검색 영역의 `PDF 텍스트 조회` input에서 영어/숫자는 검색되지만 한글은 검색되지 않았다.
- 검색은 `onRunSearch`가 no-op이고, input `onChange`로 키 입력마다 `searchPdf`를 즉시 실행하는 라이브 검색만 동작했다.

### 원인
- 한글은 IME 조합(composition) 과정을 거치는데, 조합 중간(자모 단위) 값으로 검색이 실행되고 조합 완료된 최종 한글로는 검색 트리거가 보장되지 않았다.
- Enter(`onRunSearch`)가 no-op이라 조합 완료 후 명시적으로 검색을 실행할 수단도 없었다.

### 변경 내용
- `frontend/src/components/patent-analysis/pdf/PatentPdfToolbar.tsx`
  - `isComposingRef`로 IME 조합 상태를 추적한다.
  - `onChange`는 표시값(`onSearchQueryChange`)을 항상 갱신하되, 조합 중이 아닐 때만 `onRunSearch`로 라이브 검색(영어/숫자 기존 동작 유지)을 실행한다.
  - `onCompositionStart`/`onCompositionEnd`를 추가해 한글 조합 완료 시점의 최종 값으로 검색을 실행한다.
  - `onPressEnter`/`Search` 버튼이 현재 입력 값으로 실제 검색을 실행하도록 했다(기존 Enter no-op 제거).
  - `onRunSearch` 시그니처를 `(value?: string) => void`로 변경.
- `frontend/src/hooks/usePatentPdfViewer.ts`
  - `searchPdf`에서 query를 `normalize('NFC')`로 정규화해 PDF 텍스트(대개 NFC)와 매칭이 어긋나지 않게 했다.
  - 표시 전용 갱신을 위해 `setSearchQuery`를 hook 반환에 노출했다.
- `frontend/src/pages/PatentAnalysisDetail.tsx`
  - `onSearchQueryChange`를 `setSearchQuery`(표시 전용)로, `onRunSearch`를 `searchPdf` 실행으로 분리 배선했다.

### 기대 결과
- 한글을 입력하고 조합 완료(또는 Enter) 시 PDF 본문에서 한글 텍스트가 검색·하이라이트된다(텍스트 레이어에 올바른 한글이 있는 경우).
- 영어/숫자 라이브 검색 동작은 기존과 동일하게 유지된다.

### 검증 결과 / 한계 (OCR 데이터 이슈)
- IME 경로는 정상 동작 확인: 조합 완료된 한글이 올바른 NFC 음절(예: `화합물` → `d654 d569 bb3c`)로 `utils.search`까지 전달됨.
- 라이브러리는 query를 그대로 pdf.js `eventBus.dispatch("find", ...)`로 넘기고, 매칭은 pdf.js find가 담당한다. (`PdfSearchOptions`: `caseSensitive`/`entireWord`/`highlightAll`/`matchDiacritics`만 존재, `phraseSearch`는 무효 옵션이라 제거)
- 그럼에도 한글 검색이 0건인 원인: 대상 PDF가 OCR본인데 **OCR이 한글을 정확히 텍스트화하지 못해** 텍스트 레이어의 한글이 대부분 깨진 Latin/기호로 들어가 있다(예: 초록의 "본 발명은" → `2 YS`). `발명`·`조성물` 같은 흔한 단어조차 올바른 한글로 존재하지 않아(`.includes('조성물') === false`, pdf.js 전체 문서 검색도 0건) 매칭되지 않는다.
- 결론: 프론트 검색 코드 문제가 아니라 **OCR/데이터 단 한계**. OCR이 한글을 올바르게 텍스트화하면 현재 코드 그대로 한글 검색이 동작한다.
- 디버그 로그는 원인 확정 후 제거함. IME 처리/NFC 정규화는 정당한 개선이므로 유지.

## 21. Universal Search Scaffold Options

### 배경
- 통합 검색 페이지 검색 방식 옵션에 Scaffold 검색을 추가해야 했다.
- `compound_search` 내부에는 `scaffold_query(smiles, scaffold_type)`가 있었지만 `/search` API의 `search_type` 라우팅에는 연결되어 있지 않았다.

### 변경 내용
- `frontend/src/services/compoundSearchApi.ts`
  - `CompoundSearchType`에 `bm_scaffold`, `csk_scaffold`, `pattern`을 추가했다.
  - Scaffold 검색 요청용으로 `search_type: "scaffold"`와 별도 `scaffold_type` payload를 지원하도록 했다.
  - 값 범위 필터 요청용 `filter_field`, `filter_min_value`, `filter_max_value` payload를 추가했다.
- `frontend/src/pages/UniversalSearch.tsx`
  - `검색 대상` 옵션을 추가해 `Structure`와 `Scaffold`를 분리했다.
  - `Structure` 선택 시 기존 `Substructure`, `Similarity`, `Identical` 검색 방식을 표시한다.
  - `Scaffold` 선택 시 별도 `Scaffold 기준` 옵션으로 `Pattern`, `BM Scaffold`, `CSK Scaffold`를 표시한다.
  - Scaffold 검색 선택 시 `fast` 엔진으로 자동 전환한다.
  - Scaffold 검색 중 `advanced` 엔진 선택 시 warning을 표시하고 `fast`를 유지한다.
  - `값 범위 기준` 필터를 추가했다.
    - Molecular Weight, LogP, TPSA, Heavy Atoms, HBA, HBD, Rotatable Bonds, Max Phase 중 하나를 선택한다.
    - Min/Max 중 한쪽만 입력해도 API range filter로 전달한다.
  - `값 범위 기준` 필터를 `정렬` 옵션 앞에 배치했다.
- `frontend/src/index.css`
  - 범위 필터 `InputNumber` 높이와 내부 input 세로 중앙 정렬을 맞췄다.
- `compound_search/search_api.py`
  - `/search`의 `search_type`에 `scaffold`를 추가하고 `scaffold_type`으로 `BM`, `csk`, `pattern`, `bm_scaffold`, `csk_scaffold`를 허용했다.
  - fast 엔진에서 `scaffold_type`을 `BM`, `csk`, `pattern`으로 정규화해 `SearchAgent.scaffold_query`를 호출한다.
  - 하위 호환을 위해 `search_type`에 `bm_scaffold`, `csk_scaffold`, `pattern`을 직접 보내는 기존 payload도 계속 허용한다.
  - advanced 엔진으로 scaffold 검색 요청 시 400 응답을 반환한다.
- `compound_search/elastic_search_agent.py`
  - BM scaffold field명을 실제 인덱스 필드인 `bm_scaffold`로 수정했다.

### 기대 결과
- 통합 검색에서 구조 검색 방식과 Scaffold 검색 기준이 UI상 명확히 분리된다.
- 선택한 Scaffold 기준 값이 compound_search API의 올바른 scaffold 검색 로직으로 전달된다.
- 통합 검색에서 단일 물성 필드 기준의 Min/Max 범위 필터를 함께 적용할 수 있다.
