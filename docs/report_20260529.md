## Compound IDs Patent Lookup Optimization

_Source: `report_20260529_compound_ids_patent_lookup.md`_


## 배경
- 특허 분석 목록 구조 검색은 Elasticsearch compound 검색 후 각 compound별로 `GET-PATENT-LIST-BY-COMPOUND-ID`를 호출했다.
- helper API에 `GET-PATENT-LIST-BY-COMPOUND-IDS`가 추가되어 compound id 목록을 한 번에 조회할 수 있게 되었다.

## 변경 사항
- backend 구조 검색의 특허 역조회 단계에서 bulk API를 먼저 호출하도록 변경했다.
  - `operation=GET-PATENT-LIST-BY-COMPOUND-IDS`
  - `actionType=GET-PATENT-LIST-BY-COMPOUND-IDS`
  - `compound_ids=<comma-separated ids>`
- bulk 호출이 실패하면 기존 compound별 `GET-PATENT-LIST-BY-COMPOUND-ID` 병렬 호출로 fallback한다.
- 구조 검색 2페이지 이상에서 helper의 page 조회가 실패하면 초과/빈 페이지로 보고 빈 결과를 반환하도록 방어했다.
- 초과 page에서 반환되는 total이 현재 page를 유효하게 만들지 않도록 이전 page 범위로 보정하고, frontend는 현재 page가 total 기준 마지막 page를 넘으면 마지막 유효 page로 되돌린다.
- 구조 검색 pagination을 patent row 기준으로 변경했다.
  - frontend의 `page`는 patent page로 해석한다.
  - backend는 내부적으로 compound page를 `compoundPageSize=100` 단위로 조회한다.
  - 요청 patent page가 채워질 때까지 compound page를 누적 조회하고 `publication_number` 기준으로 전역 dedupe한다.
  - 같은 구조 검색 조건은 backend 메모리 cache를 재사용한다.
  - compound page가 모두 소진되기 전까지 total은 현재 page와 다음 page만 표시되도록 반환하고, 소진 후 실제 patent row 수로 고정한다.
- backend 구조 검색 흐름을 Docker 로그에서 확인할 수 있도록 `[StructureSearch]` prefix 로그를 추가했다.
- backend `Dockerfile`을 dev 실행용으로 변경해 source 변경과 debug 로그가 dev 컨테이너에 반영되도록 했다.
- helper API 문서에 `GET-PATENT-LIST-BY-COMPOUND-IDS` operation을 추가했다.

## 참고
- helper의 `compound_ids`는 JSON array가 아니라 SQL `IN (...)`에 들어가는 comma-separated string 형식이다.
- 이 변경은 한 compound page 내 역조회 시간을 줄인다. 서로 다른 compound page에서 같은 patent가 나오는 page 간 중복 문제는 별도 pagination/cache 정책으로 다뤄야 한다.

## Dev Deploy API Runtime Env Fix

_Source: `report_20260529_dev_deploy_api_runtime_env.md`_


## Context
- Dev 서버 배포 화면(`http://172.16.1.183:18080`)에서 API 호출이 `http://localhost:3000/api/...`로 나가 CORS 에러가 발생했다.

- nginx 배포 환경에서는 entrypoint가 `env.template.js`를 `/usr/share/nginx/html/env.js`로 치환하므로 `docker-compose.dev.yml`의 `VITE_API_URL=/api`가 계속 적용된다.
- nginx runtime env 치환 스크립트가 컨테이너 시작 시 실행되도록 `frontend/Dockerfile.dev`에서 실행 권한을 부여했다.
- `backend/Dockerfile.dev`를 watch 모드 실행 대신 multi-stage build 후 `dist/main.js`를 실행하는 prod-like 이미지로 변경했다.
- dev compose backend 환경을 `NODE_ENV=production`으로 맞추고, `CORS_ORIGINS`에 dev 서버 origin `http://172.16.1.183:18080`을 추가했다.

## Structure Search Compound Table Redesign

_Source: `report_20260529_structure_search_compound_table.md`_


## 배경
- 구조 검색에서 unique patent 기준 pagination을 만들려면 Elasticsearch compound 결과를 끝까지 훑어야 했다.
- `compoundTotal=342436` 같은 검색에서는 전체 compound 수집이 backend OOM/kill로 이어질 수 있다.
- 따라서 구조 검색 화면의 기준을 patent list가 아니라 compound list로 바꿨다.

## 변경 사항
- backend 구조 검색은 요청한 compound page만 조회한다.
  - page 1: `GET-ELASTIC-COMPOUND-LIST`
  - page 2 이상: `GET-ELASTIC-COMPOUND-LIST-BY-PAGE`
- backend 응답 `items`는 compound row 목록이다.
  - `compoundId`
  - `svgImg`
  - `smiles`
  - `mw`
  - `logP`
  - `tpsa`
  - `patentCount`
- `patentCount`는 helper 응답의 `substructure.num_per_patent` 값을 사용한다.
- 첫 구조 검색 응답에는 compound별 특허 목록을 포함하지 않는다.
- compound row를 펼칠 때 `/api/patents/compounds/:compoundId/patents` API로 특허 목록을 lazy load한다.
- backend `totalCount`는 Elasticsearch의 compound total을 그대로 반환한다.
- frontend 구조 검색 모드는 compound table을 표시한다.
- compound row를 펼치면 해당 compound에 연결된 특허 목록을 하위 table로 표시한다.
- 일반 특허 제목/번호 검색 화면은 기존 patent table을 유지한다.
- Elasticsearch deep pagination 한계로 구조검색 compound pagination은 상위 10,000개 결과까지만 이동 가능하게 제한했다.
  - 실제 `compoundTotal`은 pagination 문구에 표시한다.
  - backend도 10,000개 이후 offset 요청은 helper 호출 전에 400으로 차단한다.

## 설계 효과
- pagination 기준이 compound total로 고정되어 페이지 수가 흔들리지 않는다.
- 전체 compound를 backend 메모리에 모으지 않으므로 OOM 위험이 낮다.
- 같은 patent가 여러 compound에 걸쳐 중복 표시될 수 있지만, compound 중심 검색 결과에서는 자연스러운 표현이다.
