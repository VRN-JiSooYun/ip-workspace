# 검색어 칩 — 근거 칩도 지우기, 칩 클릭은 OR 조건에 넣기

## 요구

1. `pm-doc-search-chip-evidence`(검색 근거 칩)도 지울 수 있게 한다.
2. 칩을 눌러 active로 만들면 **PDF 검색의 OR 조건에 추가**한다
   (누를 때마다 다음 결과로 넘기던 동작에서 바꾼다).

## 결과

칩이 **라디오 버튼에서 토글**로 바뀌었다. 켠 칩 전부가 하나의 검색으로 걸리고, 결과 사이
이동은 toolbar의 ‹ › 가 맡는다. 근거 칩과 사용자 칩 모두 × 로 트레이에서 내릴 수 있다.

## OR은 흉내가 아니라 pdf.js의 다중 검색어다

pdf.js `PDFFindController.match`는 query로 **문자열 배열**을 받아 `(a)|(b)` 정규식으로 엮는다.
그래서 개수·순서·다음/이전 이동이 전부 하나의 검색으로 다뤄진다 — 칩마다 따로 검색을 걸어
합치는 방식(그러면 `3/12`가 무엇의 3인지 알 수 없다)을 쓰지 않았다.

배열을 쓰려고 넘어야 할 것이 두 가지 있었다.

### 1. 라이브러리의 `search()`는 배열에서 죽는다

`react-pdf-highlighter-plus`의 `utils.search(query)`는 `query.trim()`을 부른다. 배열이면 그
자리에서 `TypeError`다. 그 함수가 하는 일은 `find` 이벤트 dispatch뿐이므로, **배열일 때만**
같은 payload를 event bus에 직접 올린다(`dispatchPdfFind`). 검색어가 하나면 예전처럼
라이브러리 공개 API를 그대로 쓴다 — 특허 분석 화면 등 기존 경로의 동작을 건드리지 않으려고
갈랐다.

같은 이유로 다중 검색어일 때는 `utils.findNext()`도 쓸 수 없다(라이브러리가 자기 ref에 담아
둔 마지막 검색어를 되쓴다). 그때는 같은 배열로 `type: 'again'`을 직접 올린다.

### 2. 공백 무시 어댑터가 배열을 그냥 통과시키고 있었다

`installWhitespaceTolerantPdfSearch`는 PDF의 줄바꿈(EOL → 공백) 때문에 `제출기일`이
`제출기 일`로 끊기는 문제를 풀려고 `match`를 감싼 것인데, 주석 그대로 **문자열만** 처리하고
배열은 원본 구현으로 넘겼다. 그대로 두면 칩 두 개를 켜는 순간 줄바꿈을 넘는 검색어가 조용히
빠진다. 배열도 각 검색어를 압축해 같은 규칙으로 찾도록 고쳤다.

PDF.js가 넘어온 배열을 제자리에서 정렬하므로(`query.sort().reverse()`) 호출자의 배열을 그대로
넘기지 않고 압축한 사본을 넘긴다.

## 입력창과 칩의 관계

toolbar 입력창은 낱말 하나짜리 칸이다. 그래서 켠 칩이 **하나면** 그 낱말을 입력창에 넣고,
**둘 이상이면 비운다** — 무엇이 걸렸는지는 칩이 말한다(개수 `7/21`과 ‹ › 는 그대로 동작한다).
입력창에 직접 치면 그 순간 PDF에 걸린 것은 그 낱말 하나뿐이므로 켜 둔 칩을 모두 끈다.

## 근거 칩을 지운다는 것

근거 칩은 검색 조건에서 파생되므로 목록에서 빼는 것만으로는 지워지지 않는다(다음 렌더에 다시
만들어진다). 그래서 '지웠다'를 따로 기억한다(`dismissedTerms`).

- 문서를 옮겨도 남는다 — 같은 검색의 같은 낱말이라 문서마다 다시 물어볼 일이 아니다.
- **검색 조건이 바뀌면 잊는다** — 트레이 내용 자체가 새로 만들어지는 시점이다.
- 같은 낱말을 toolbar에서 다시 쳐서 쌓으면 다시 보여 준다.

## 문서를 옮겼을 때 무엇을 켤지

규칙 셋으로 정리했다.

1. 켜 두었던 칩 중 **새 문서의 트레이에도 있는** 것은 그대로 켜 둔다(칩 없는 하이라이트가
   남으면 무엇이 칠해진 것인지 알 수 없다).
2. 새 문서의 근거 칩이 있으면 그 첫 번째를 켠다.
3. 그래도 켤 것이 없으면 첫 사용자 칩으로 내려간다.

## 검증

`office-action-harness.html`에 실제 PDF(281쪽 WO 공보)를 임시로 물려 측정했다. 개수 배지는
전문을 따로 읽어 센 값이고 `n/총계`는 pdf.js가 센 값이라, 둘을 견주면 OR이 실제로 걸렸는지
알 수 있다.

| 켠 칩 | 각 칩 개수 | toolbar 총계 | 읽는 법 |
| --- | --- | --- | --- |
| `INTERNATIONAL SEARCH` | 7 | **7** | 단일 검색어 |
| + `INTERNATIONAL` | 7, 21 | **21** | 긴 쪽이 짧은 쪽을 품어 자리 수는 21 |
| `INTERNATIONAL`만 | 21 | **21** | 칩을 끄면 그만큼 빠진다 |
| + `SEARCH` | 21, 15 | **36** | 21 + 15 — 겹치지 않는 두 낱말의 합 |
| `PATENT` + `SEARCHREPORT` | 15, 6 | **21** | 15 + 6 |

마지막 줄이 공백 무시 어댑터까지 확인한다. `SEARCHREPORT`는 PDF 원문에 `SEARCH REPORT`로
띄어져 있어 **공백을 지운 사본에서만** 찾히는 검색어다. 배열 경로가 어댑터를 타지 않았다면
0건이 되어 총계가 15에 머물러야 하는데 21이 나왔다.

그 밖에 확인한 것:

| 확인 | 결과 |
| --- | --- |
| 근거 칩 × | 세 근거 칩 모두 × 가 붙어 있고, 눌러서 트레이에서 사라짐 |
| 켜 둔 근거 칩을 지움 | 총계 23 → 21로 되돌아 남은 칩으로 다시 걸림 |
| 지운 근거의 지속 | 다른 결과를 열었다 돌아와도 다시 나타나지 않음 |
| 검색 조건 변경 | 새 조건으로 검색하니 지웠던 `SEARCH`가 근거 칩으로 복귀 |
| 문서 이동 | 켜 둔 사용자 칩은 유지되고 새 문서의 첫 근거 칩이 함께 켜짐 |
| ‹ › (다중 검색어) | 8/36 → 9 → 10 → 11, 이전으로 10 — 'again' 직접 dispatch 경로 동작 |
| toolbar 직접 검색 | 칩 선택이 풀리고 입력값은 유지됨(기존 동작 그대로) |
| 칩 커밋 | Search 버튼으로 쌓으면 그 칩만 켜지고 입력창이 비워짐 |
| 입력창 표시 | 켠 칩 1개면 그 낱말, 2개 이상이면 빈칸 |
| harness | 10/10 통과 |

`tsc -b --force`: 이 변경과 관련된 오류 없음.

임시로 넣은 PDF(`frontend/public/__or-test.pdf`)와 harness의 임시 `documentPath`·본문·
`/content` stub 수정은 모두 되돌렸다(`git status`로 확인).

## 남은 것(이 작업과 무관)

- `PatentRecordDetailModal.tsx`의 type 오류 5건 — 작업 트리에 이미 있던 미완성 편집.
- harness의 "키워드가 없으면 전문 Search API를 호출하지 않는다"는 측정 중에 직접 검색을 하면
  실패로 잡힌다(측정 후 검색한 호출까지 세기 때문). 다시 측정하면 통과한다.

# 후속 — 새 검색어는 켜 둔 칩에 **더한다**

## 요구

칩 토글이 켜진 상태에서 toolbar에 새 검색어를 입력하면 켜져 있던 칩이 꺼졌다.
켜 둔 것을 유지한 채 새 검색어를 append해야 한다.

## 무엇이 꺼뜨렸나

두 군데였다.

1. **치는 동안** — `onSearchQueryChange`가 `onManualSearch()`를 불러 켜 둔 칩을 전부 껐다.
   활성 검색어가 하나였던 시절의 규칙이다(입력창과 칩이 같은 자리를 다투었다).
2. **쌓는 순간** — `addTerm`이 `setActiveTerms([term])`으로 목록을 방금 입력한 낱말 하나로
   갈아치웠다.

## 고친 내용

- `onManualSearch`를 없앴다(pane·`FullTextPane`의 prop과 toolbar 세 handler에서 함께 제거).
  이제 입력창은 칩을 건드리지 않는다 — 칩은 OR 목록이고 입력창은 그 목록에 넣을 낱말을 적는
  칸이다.
- `addTerm`이 목록에 **더한다**. 이미 있는 낱말이면 목록은 그대로 둔다.
- `addTerm`이 요청 번호를 올린다. **이것이 없으면 안 된다** — toolbar는 방금 입력한 낱말
  하나로만 검색을 걸어 둔 상태라, 목록 전체로 다시 걸어야 앞서 켜 둔 칩이 빠지지 않는다.
  이미 켜 둔 낱말을 다시 쳐서 쌓는 경우(목록이 그대로인 경우)도 이 번호 덕에 되돌아온다.

## 딸린 규칙 변경 — 입력창은 사용자가 친 것만 담는다

`searchPdf`가 **배열로 불릴 때는 입력창 표시값을 건드리지 않는다**(문자열은 그대로 넣는다).

앞선 규칙("켠 칩이 하나면 그 낱말을 입력창에 넣는다")을 그대로 두면 새 규칙과 충돌한다.
칩을 쌓은 직후 목록이 한 개면 방금 비운 입력창에 그 낱말이 다시 적히고(칩과 입력창에 같은
낱말이 겹친다), 치는 중에 칩을 켜면 치던 값이 지워진다.

같은 이유로 pane이 목록을 비울 때도 `searchPdf('')`가 아니라 `searchPdf([])`로 지운다.

## 검증

앞 절과 같은 임시 구성(281쪽 WO 공보)으로 측정했다.

| 단계 | 칩 상태 | 총계 | 입력창 |
| --- | --- | --- | --- |
| 근거 칩 1개 자동 | `INTERNATIONAL SEARCH`[ON] | 7 | 빈칸 |
| `SEARCH` 칩도 켬 | 2개 [ON] | 15 | 빈칸 |
| toolbar에 `PATENT` 입력(커밋 전) | **2개 [ON] 유지** | 15 | `PATENT` |
| Search로 쌓음 | **3개 [ON] + `PATENT`[ON]** | **30** = 15+15 | 비워짐 |
| 이미 켠 `SEARCH`를 다시 입력 | 4개 [ON] 유지, 칩 중복 없음 | 15 → **30** 복귀 | 비워짐 |

마지막 줄이 요청 번호의 몫을 보여 준다 — 목록이 바뀌지 않았는데도 15(그 낱말만)에서
30(목록 전체)으로 되돌아온다.

harness 10/10 통과, `tsc -b --force` 관련 오류 없음. 임시 PDF와 harness 수정은 되돌렸다.

# 후속 — 지우기 버튼을 칩과 한 몸으로

## 요구

`pm-doc-search-chip`의 `pm-doc-search-chip-remove`가 칩과 일체가 아니어서 이질적이다.

## 무엇이 어긋나 있었나

두 버튼이 각자 antd 버튼의 면을 갖고 서로 이어 붙는 구조였다. 측정해 보면 한 알약 안의 두
조각이 실제로 다른 물건이었다.

| | 검색어 쪽 | 지우기 쪽 |
| --- | --- | --- |
| 테두리 색 | `rgb(217,217,217)` (antd 기본) | `rgb(240,240,240)` (`--border-color`) |
| 면 | 흰색(`--card-bg`) 또는 브랜드 | 투명 — 트레이의 옅은 브랜드 배경이 비친다 |
| 이음매 쪽 radius | 0 | **6px** (antd 기본이 남아 있었다) |
| 켠 칩 | 브랜드 면 + 흰 글자 | 회색 글자 + 회색 테두리 |

그래서 켠 칩은 "브랜드 알약에 흰 꼬리가 붙은" 모양이었고, 끈 칩도 이음매에서 테두리 색과
radius가 어긋났다.

## 고친 방식 — 알약은 칩이 그린다

껍데기(`.pm-doc-search-chip`)가 테두리·면·radius·상태 색을 갖고, 안쪽 두 버튼은 면 없이
얹힌다.

- 안쪽 antd 버튼은 `border: none; background: transparent; box-shadow: none; color: inherit`.
  라벨 쪽 버튼도 `type="primary"/"default"`에서 **`type="text"`**로 바꿨다 — 면을 칩이
  칠하므로 알약 안에 또 알약이 들어앉을 이유가 없다.
- 두 조각은 `align-items: stretch`로 칩 높이를 그대로 채운다(24px 칩 안에서 둘 다 22px).
- 바깥쪽 끝만 999px로 둥글리고 이음매 쪽은 각지게 둔다.
- 가르는 것은 **머리카락 한 줄**뿐이다: 지우기 쪽 `border-inline-start` 1px. 끈 칩은
  `--border-color`(칩 자신의 테두리와 같은 값), 켠 칩은 `rgba(255,255,255,0.4)`.
- 어느 쪽을 누르게 되는지는 **조각별 hover 면**으로 알린다 — 끈 칩은
  `rgba(브랜드,0.12)`, 켠 칩은 `rgba(255,255,255,0.18)`.

### 선택자를 트레이까지 적은 이유

antd v5의 버튼 규칙은 런타임에 이 파일보다 **뒤에** 끼워진다. class 하나(`.pm-doc-search-…`)
로는 radius·색이 antd 값으로 되돌아가서, 안쪽 버튼 규칙은 `.pm-doc-search-tray`까지 적어
무게를 올렸다.

### 다크 모드에서 하나 더 고쳤다

켠 칩의 글자색이 `var(--card-bg)`였다. 라이트에서는 흰색이지만 다크에서는 `#1f1f1f`라
**주황 면 위에 거의 검은 글자**가 된다. 브랜드 면은 두 테마가 같은 색이므로 그 위의 글자도
흰색으로 고정했다(근거 점도 같은 이유로 흰색 고정).

## 검증

실제 PDF를 물린 harness에서 계산값과 화면을 함께 봤다.

| 확인 | 값 |
| --- | --- |
| 높이 | 칩 24 / 라벨 22 / 지우기 22 (테두리 1px씩 뺀 값, stretch로 맞음) |
| 이음매 틈 | 0px (라벨 오른쪽 = 지우기 왼쪽) |
| radius | 라벨 `999 0 0 999`, 지우기 `0 999 999 0` |
| 면 | 칩만 칠한다 — 두 버튼 모두 `transparent`, 테두리 0 |
| 가름선 | 끈 칩 1px `--border-color`, 켠 칩 1px `rgba(255,255,255,0.4)` |
| 색 상속 | 지우기 색 = 칩 색 (켠 칩 흰색, 끈 칩 `--text-secondary`) |
| hover | 지우기에 올리면 그 조각만 `rgba(브랜드,0.12)`, 칩 테두리는 `rgba(브랜드,0.5)` |
| 라이트/다크 | 켠 칩은 두 테마 모두 브랜드 면 + 흰 글자·흰 × |
| 개수 0(비활성) 칩 | 라벨만 흐려지고(opacity 0.55) 지우기는 그대로 — 없는 검색어일수록 내리고 싶다 |

harness 10/10, `tsc -b --force` 관련 오류 없음. 임시 PDF와 harness 수정은 되돌렸다.
